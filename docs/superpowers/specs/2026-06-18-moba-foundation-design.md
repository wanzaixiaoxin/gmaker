# MOBA 可玩对局底座设计（产品 + 技术双线规划）

**日期**: 2026-06-18
**角色**: 制作人（顶层）、主策划（产品线）、技术负责人（技术线）
**状态**: 已确认方向，待 spec review

---

## 0. 已确认的设计约束（制作人顶层框定）

本节是主策划与技术负责人共同的不可逾越约束，由制作人在 brainstorming 阶段定调：

| 项 | 定调 | 含义 |
|---|---|---|
| **同步模型** | 确定性帧同步，纯服务端权威 | 技术地基唯一约束；客户端零信任、只渲染 |
| **底座目标** | 5v5 可跑完一局的**可玩对局底座** | 不含排位/社交/商业化 |
| **交付物边界** | 确定性引擎 + 5v5 地图/英雄/经济/复活/胜负循环 | 2-3 英雄验证 kit 差异 |
| **模拟位置** | 纯服务端权威模拟 | 客户端不跑模拟；定点数库只需 C++ 单端 |

### 协同铁律（制作人仲裁依据）

1. **产品定"玩家能感知什么"，技术定"如何确定性地实现"** —— 主策划不越界定数值精度，技术不越界改手感。
2. **确定性不可妥协** —— 任何产品需求若引入非确定性，技术有权拒绝并提替代方案。
3. **配置驱动** —— 所有数值/地图/英雄 kit 走配置文件，禁止硬编码进代码。
4. **手感量化** —— 所有"手感"诉求必须翻译为可测指标（tick 数、延迟、判定半径），不接受主观描述。
5. **不接非契约需求** —— 产品需求必须经闸门 A（需求清单评审）进入技术排期。

### 底座成功标准（产品与技术联合终验）

一场 5v5 对局，从匹配→加载→倒计时→对战（移动/技能/经济/复活）→水晶推平→结算，**全流程可玩、可重连、可回放**。英雄仅 2-3 个用于验证 kit 差异。

## 1. 主策划产品线

### 1.1 产品方向

> **"用最小的内容量（2-3 英雄、1 张 5v5 地图），把 MOBA 一局对战的核心心流完整跑通——让玩家在 15 分钟内体验到'对线→博弈→成长→决胜'的完整循环，并验证这套循环在确定性帧同步下是可信赖的。"**

核心心流的四个阶段（产品组的验收锚点，每一阶段都要"可感知、可博弈、有反馈"）：

| 阶段 | 玩家心流 | 底座必须验证的博弈点 |
|---|---|---|
| **对线期**（0-5min） | 补刀/消耗/控线 | 兵线经济、技能消耗博弈、塔下安全性 |
| **博弈期**（5-10min） | gank/反 gank、控野 | 视野与草丛、野区资源争夺 |
| **成长期**（持续） | 滚雪球/翻盘 | 等级/装备带来的质变点 |
| **决胜期**（10-15min） | 抱团推塔/守高 | 水晶胜负、复活节奏控制 |

关键产品原则：
- **手感底线**：输入到可见反馈 ≤100ms（纯服务端权威下靠 server tick 率 + 客户端插值保证）
- **确定性信任**：同一局输入回放必须产出相同结果（产品"公平"的根基，主策划用回放一致性测试验收）
- **内容克制**：底座阶段 2-3 英雄，每个验证一种不同的战斗范式

### 1.2 英雄设计方向（验证底座承载力）

底座只做 3 个英雄，每个验证一种范式：

| 英雄代号 | 范式 | 验证底座的什么能力 |
|---|---|---|
| **战士（近战持续）** | 平 A + 短 CD 位移 | 移动碰撞、普攻判定、近身缠斗 |
| **法师（远程爆发）** | 蓄力 + AOE + 弹道 | 弹道物理、范围伤害、技能 CD 体系 |
| **刺客（位移爆发）** | 突进 + 斩杀 + 隐身 | 视野/隐身机制、位移穿墙、斩杀线 |

注：刺客的"隐身"同时是**视野系统的产品验证用例**——主策划用隐身英雄逼迫技术组把视野（fog of war）做出来，否则刺客无法成立。

### 1.3 经济与成长循环

```
击杀/助攻/补刀/野怪 → 获得金币 + 经验
   ├── 经验 → 升级（1-15级） → 技能点（Q/W/E 升级，R 在 4/8/12 级解锁） → 数值成长
   └── 金币 → 装备（底座做 6-8 件基础装） → 数值/机制质变（如位移鞋、暴击剑）
死亡 → 复活倒计时（随等级增长） → 在泉水复活 → 重新参战
```

底座阶段做减法（YAGNI）：
- 装备只做 6-8 件，覆盖"攻击/防御/机动"三类基础质变，不做装备合成树
- 符文/天赋系统**不做**（底座阶段）
- 野怪只做 2 种：小野（经验金币）+ 大龙/暴君（团队增益 buff），验证 buff 体系

### 1.4 地图设计

```
        蓝方基地（水晶）
         上路（长）
    野区A ─── 中路 ─── 野区B
         下路（短）
        红方基地（水晶）

要素：3路 + 2片野区 + 河道 + 草丛（视野） + 泉水（复活/回血）
塔：每路 外塔→内塔→高地塔→水晶（4级），共 22 塔
```

底座阶段地图做减法：
- 地形碰撞用简化的格点/导航网格，不做复杂寻路
- 草丛做圆形视野遮挡区，不做复杂多边形视野计算
- 河道/野区做实体生成点，野怪定时刷新

### 1.5 产品组角色分工

底座阶段产品组精简为 4 个角色：

| 角色 | 职责 | 交付物 | 与技术组对接 |
|---|---|---|---|
| **主策划** | 产品方向、阶段验收、跨组协同铁律仲裁 | 产品方向文档、阶段验收标准 | 技术负责人 |
| **战斗策划** | 英雄 kit、技能数值、战斗手感、平衡性 | 英雄设计文档（3 个）、技能数值表、战斗节奏曲线 | 战斗引擎工程师 / 前端工程师 |
| **关卡策划** | 地图结构、野区/兵线/塔布局、视野设计 | 地图编辑数据（格点+实体点）、波次配置 | 服务端战斗工程师 |
| **数值策划** | 经济曲线、成长公式、装备数值、复活时间表 | 数值表（TOML/CSV 配置）、成长公式文档 | 配置/数据工程师 |

关键分工原则：
- **数值策划用配置表表达，不写代码** —— 所有数值以 TOML/CSV 配置形式交付，由配置工程师接入战斗引擎。保证数值调整不需要发版。
- **战斗策划的"手感"诉求转化为可验收指标** —— 例如"位移技能响应快"→ 量化为"位移指令到位移开始的 server tick 数 ≤ 2"。手感争议通过指标仲裁。
- **关卡策划的地图数据走数据驱动** —— 地图不是硬编码在 C++ 里，而是配置文件驱动的格点+实体点数据。

### 1.6 产品侧流程管线

```
[阶段1 需求定义] → [阶段2 原型验证] → [阶段3 内容填充] → [阶段4 调优平衡] → [阶段5 验收]
     ↓ 闸门A          ↓ 闸门B            ↓ 持续协同        ↓ 闸门C            ↓ 闸门D
```

**阶段 1：需求定义（产品侧先行）**
- 入口：制作人顶层框定已确认
- 产出：英雄 kit 文档、地图结构草案、经济/成长公式草案
- 协同闸门 A（与技术）：产品需求评审会。主策划交付**需求清单**（每个英雄技能需要什么底层能力：位移？弹道？隐身？buff？），技术评估可行性并反馈技术约束。**需求清单是产品↔技术的第一份契约。**

**阶段 2：原型验证（产品与技术并行）**
- 产品侧：战斗策划用"灰盒英雄"（临时数值）验证 kit 手感方向；关卡策划用占位地图验证兵线/塔节奏
- 协同闸门 B：每周一次**可玩性走查**。产品在技术提供的灰盒环境里实玩，记录手感问题清单（量化为 tick/延迟指标），技术按优先级排期
- 关键：此阶段数值全是临时的，不追求平衡，只验证"循环跑得通、手感方向对"

**阶段 3：内容填充（产品与技术并行）**
- 产品侧：数值策划填正式数值表（TOML）、战斗策划细化技能表现、关卡策划定稿地图配置
- 持续协同：数值配置通过配置系统热加载，产品可随时改数值不需技术发版
- 协同闸门 C（中段验收）：核心循环可玩性验收。主策划按"四阶段心流"清单逐项验收

**阶段 4：调优平衡（产品主导）**
- 产品侧：战斗策划 + 数值策划基于实玩数据调整平衡
- 技术支持：技术提供**回放系统 + 战斗日志**（确定性帧同步的副产品），产品用回放复盘平衡问题
- 此阶段技术基本不再改动战斗逻辑，只修 bug

**阶段 5：底座验收（产品与技术联合）**
- 协同闸门 D（终验）：完整对局验收标准（见 0.x 成功标准）

### 1.7 产品侧三条铁律

1. **配置驱动**：所有数值/地图/英雄 kit 走配置文件，禁止硬编码进代码
2. **手感量化**：所有"手感"诉求必须翻译为可测指标，不接受主观描述
3. **不越界实现**：产品组不指定技术实现方案，只描述玩家感知；技术实现完全由技术负责人定

技术选型定调：
- **确定性引擎语言**：C++（性能 + 已有 ComputePool）。纯服务端权威，定点数库只需 C++ 单端，客户端不跑模拟，Go 不参与战斗。
- **配置驱动**：产品数值表（TOML/CSV）由 config-go 热加载，通过 RPC 下发给 realtime-cpp。
- **协议**：已有 protobuf 链（已完成重构），复用。新增帧同步下行消息。

### 2.2 核心问题解决方案

#### 核心问题 1：非确定性模拟 → 重写为确定性引擎（最关键）

根因回顾：当前 `battle_room.cpp` 用墙钟 `delta_ms` 驱动模拟，浮点运算跨平台不一致。

**方案：**

**(a) 定点数数学库（新建 `common/cpp/realtime/fixed/`）**
- 用 **32.32 定点数**（整数部分 32 位覆盖地图坐标范围 ~100 单位 + 余量；小数部分 32 位提供亚毫米精度）。技术负责人在 M0 阶段用一次基准测试确认精度足够后定稿，不在 spec 阶段反复纠结。
- 实现：`Fixed` 类型 + 基本运算（加减乘除、sqrt、sin/cos 查表）+ `FixedVec3` + `FixedTransform`
- 铁律：战斗引擎内禁止出现任何 `float`/`double`，编译期用类型 trait 或 clang-tidy 检查拦截
- sqrt/sin/cos 用查表法（确定性），不用硬件指令（非确定性）

**(b) 确定性模拟循环（重写 `TickAll` → `TickFrame`）**
```
旧：TickAll(delta_ms)  // 墙钟驱动，非确定性
新：TickFrame(frame_inputs)  // 纯输入驱动
    - 固定逻辑步长（固定 step = 定点数常量）
    - 无 now_ms，无 delta，所有运动 = 速度 × 固定step
    - 随机数用确定性 PRNG（xorshift，seed 来自房间初始化）
    - 集合遍历用有序容器（map 而非 unordered_map，保证遍历顺序确定）
```

**(c) 确定性校验工具（技术组测试基建）**
- 帧哈希：每帧结束计算实体状态哈希（SerializeToBytes → hash），记入日志
- 回放一致性测试：录制一局输入序列 → 在干净环境回放 → 比对每帧哈希。任何一帧不一致 = 确定性 bug。
- 集成到 CI：每次战斗引擎改动自动跑回放测试。

#### 核心问题 2：帧缓冲退化为单帧 → 真正的帧队列

根因回顾：当前 `TryAdvance` 只看 `current_frame_` 一帧，无法追赶。

方案：重写 `LockstepEngine` 的帧缓冲为滑动窗口：
- 收集未来 N 帧的输入（N=缓冲深度，如 4 帧）
- `TryAdvance` 循环确认所有已就绪帧，一次推进多帧
- 超时填空策略保留，但只在缓冲耗尽时触发（而非每帧）

#### 核心问题 3：全量广播带宽 → 增量 + 压缩

根因回顾：60fps 全量序列化所有实体，5v5 实体 30+ 带宽爆炸。

方案（分两步，按里程碑推进）：
- **M1 阶段（必做）**：降低状态同步频率。逻辑帧 30Hz，下行广播 15Hz（客户端插值补到 30/60 渲染帧）。先用全量广播跑通。
- **M3 阶段（5v5 必做）**：增量同步。只下发"本帧变化的实体"（dirty flag），未动实体不发。M1 的全量广播在 5v5 实体规模下带宽会超预算，M3 必须切增量。

带宽预算（技术负责人测算）：
- 5v5，30 实体，每实体 protobuf ~50 字节，15Hz，增量平均 1/3 实体变化
- ≈ 30 × 50 × 0.33 × 15 ≈ 7.4 KB/s/玩家，可接受

#### 核心问题 4：塔无冷却/无复活/无经济 → 战斗逻辑补全

| 产品需求 | 技术实现要点 |
|---|---|
| 塔攻击有冷却 | 塔 entity 加 `attack_cooldown` 字段，定点数计时 |
| 死亡复活 | 英雄加 `respawn_timer`，死亡转 Dead 态，计时结束在泉水复活 |
| 经验/升级 | `HeroEntity` 加 `exp_/level_`，`AddExp` 触发升级，升级解锁技能点 |
| 金币/装备 | `gold_` 接商店（底座：本地配置表购买） |
| 视野/隐身 | 格点 AOI + 视野半径，刺客隐身 = 视野半径临时为 0 |

### 2.3 技术组角色分工（6 个角色）

| 角色 | 职责 | 交付物 | 对接产品 |
|---|---|---|---|
| **技术负责人** | 框架、核心攻关、跨组仲裁 | 技术架构文档、确定性方案 | 主策划 |
| **战斗引擎工程师** | 确定性引擎、定点数库、帧同步调度器 | 定点数库、TickFrame、帧哈希工具 | 战斗策划 |
| **服务端战斗工程师** | ComputePool 集成、广播、配置接入、重连/回放 | 增量广播、配置热加载、回放服务 | 关卡策划 |
| **接入/网络工程师** | Gateway 适配、协议演进、带宽监控 | 帧同步协议消息、带宽埋点 | （内部） |
| **配置/数据工程师** | config-go 配置系统、数值表/地图数据管线 | 配置框架、数值表 schema | 数值策划 |
| **前端工程师** | 客户端渲染、插值、输入采集、视野渲染、回放/重连 UI | 客户端渲染层、插值算法、输入编码 | 战斗策划（手感） |

#### 前端工程师职责边界（技术负责人划清，防职责模糊）

底座选了"纯服务端权威、客户端零信任"，前端不跑模拟、不持有权威状态。前端有三块硬骨头：

**1. 插值渲染（手感核心）**
- server 下行 15Hz 帧确认，客户端渲染 60fps，中间 45 帧靠插值补足
- 实现：实体位置用线性插值 + 速度预估（prev→cur 外推），基于时间戳的插值缓冲（收到帧存入 buffer，渲染时读 buffer 中"过去某时刻"状态插值）

**2. 输入采集与上行**
- 采集玩家输入（移动方向、技能释放、目标选择）→ 编码为 protobuf → 上行
- 输入去重 + 节流（避免 60fps 刷爆上行带宽）

**3. 视野渲染（fog of war）**
- server 下发的快照已含视野判定（server 权威决定"玩家能看到哪些实体"），前端只做视野外区域的遮挡渲染（战争迷雾效果）

**4. 回放/重连恢复**
- 回放器 UI：读取录制文件，逐帧重放
- 重连恢复：断线重连后，接收 checkpoint + 帧追赶，插值追上当前时刻

前端工程师对接边界：

| 边界 | 前端做 | 前端不做 |
|---|---|---|
| 状态权威 | ❌ | server 持有 |
| 插值/外推 | ✅ 客户端渲染层 | |
| 输入编码 | ✅ 采集+protobuf 编码 | 模拟逻辑 |
| 视野判定 | ❌ | server 算 |
| 视野渲染 | ✅ 迷雾遮挡 | |
| 数值 | ❌ | 数值策划配置表 |

### 2.4 技术侧流程管线（与产品闸门咬合）

```
[M0 确定性地基] → [M1 帧同步重构] → [M2 实体系统] → [M3 产品功能承接] → [M4 验收支撑]
   ↓ 闸门A前置      ↓ 闸门B          ↓              ↓ 闸门C            ↓ 闸门D
```

| 里程碑 | 技术交付 | 对应产品闸门 |
|---|---|---|
| **M0 确定性地基** | 定点数库、确定性 PRNG、帧哈希工具、回放测试基建 | 闸门 A 前置（技术能力评估） |
| **M1 帧同步重构** | LockstepEngine 滑动窗口、TickFrame 重写、去墙钟、确定性校验通过 | 闸门 B（灰盒环境可玩） |
| **M2 实体系统** | 英雄/小兵/塔/野怪/弹道/视野实体，碰撞与 AOI | （产品内容填充并行） |
| **M3 产品功能承接** | 塔冷却、复活、经济、升级、装备、视野（按需求清单） | 闸门 C（核心循环验收） |
| **M4 验收支撑** | 回放器、重连、带宽监控、平衡数据导出 | 闸门 D（终验工具） |

前端工程师交付（按里程碑）：

| 里程碑 | 前端交付 | 对应产品闸门 |
|---|---|---|
| **M1 帧同步重构** | 帧确认消息的客户端解码 + 基础插值 | 闸门 B |
| **M2 实体系统** | 实体渲染、移动/攻击动画表现 | （并行） |
| **M3 产品功能承接** | 视野迷雾渲染、技能特效、复活/经济 UI 表现 | 闸门 C |
| **M4 验收支撑** | 回放器 UI、重连恢复体验 | 闸门 D |

### 2.5 技术侧三条底线

1. **确定性不可妥协**：任何产品需求若引入非确定性，技术有权拒绝并提替代方案。确定性是底座根基，高于任何单个特性。
2. **配置先行**：技术提供配置 schema 后，产品数值调整不需技术介入。但产品改配置 schema（新增字段）必须走技术评审。
3. **不接非契约需求**：产品需求必须经闸门 A 进入技术排期。闸门外需求技术有权拒收。

## 4. 不做（YAGNI，明确排除）

底座阶段以下内容**不做**，避免范围蔓延：

- 排位/天梯系统
- 好友/组队/社交
- 战绩/历史
- 商业化（皮肤/付费）
- 符文/天赋系统
- 装备合成树（只做基础装直购）
- 多地图（只做 1 张 5v5）
- 英雄数量 >3（只验证 kit 差异）
- 客户端预测（纯服务端权威，客户端只插值渲染）
- 客户端跑模拟（零信任）

这些留给底座交付后的下一个迭代周期。
